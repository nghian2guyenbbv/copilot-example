LangGraph4j Incident-Response Agent

A Spring Boot 3 / Java 17 / Maven application where an AI agent receives a system alert (e.g. "High CPU and connection pool exhaustion on payment-service"), investigates, plans a fix, pauses for human approval before any dangerous command, executes the fix, and verifies recovery in a loop. State and data live in Microsoft SQL Server (Docker Compose).

3. The agent graph

START→ dispatch→ fan-out →
lookup_history lookup_runbooks scan_metrics
→ fan-in → decide (LLM)→ approval_gate ⏸ INTERRUPT→ execute→ verify→ END
  • Parallel investigation: the three lookup nodes run in the same superstep, each writing a different state key and its own audit row.
  • Risk routing: after decide, HIGH risk goes through approval_gate; LOW/MEDIUM goes straight to execute.
  • Human in the loop: the graph is compiled with interruptBefore("approval_gate"). It stops, persists state, and waits. Rejection ends the incident with nothing executed.
  • Retry loop: if verify finds the system still unhealthy, the graph returns to dispatch (max 3 attempts, then ESCALATED). A new dangerous plan asks for approval again.

4. Graph components (incident/graph)

Class / nodeResponsibility
IncidentGraphConfigSpring @Configuration that builds and compiles the StateGraph bean: nodes, edges, conditional routing, interrupt, checkpoint saver.
IncidentNodesContains all node logic (below), writing audit rows to the DB.

  lookup_runbooksLoads the service's runbooks from the Runbooks table.
  scan_metricsUses the fetchServiceMetrics tool and derives findings (high CPU, pool exhausted, leak).
  decideBuilds a DecisionContext, asks the LLM, creates a RemediationStep, increments the attempt counter.
  approval_gateRuns after a human decision is written to state; records APPROVED or REJECTED.

  verifyRe-reads the latest metrics; healthy means CPU < 70% and pool usage < 70%. Sets RESOLVED / RETRYING / ESCALATED.
SimulatedEnvironmentStand-in for kubectl/psql. Each action appends a new ServiceMetrics row (scale out halves CPU; killing sessions is undone by the leak; restart clears the leak). Also seeds an unhealthy service and runbooks on first alert.
RemediationStepSerializable record: command, dangerous, reason. Must be serializable to be checkpointed.

Primary keys use SQL Server IDENTITY. The four *Repository interfaces are Spring Data JPA repositories. IncidentTools exposes the agent tools queryActiveIncidents() and fetchServiceMetrics(service), which read real rows.

8. Durable checkpointing (SqlServerCheckpointSaver)

  • Extends LangGraph4j AbstractCheckpointSaver and stores each checkpoint as a row in lg_checkpoints (state serialized to NVARCHAR(MAX)).
  • Creates the table itself at startup if missing.
  • Each insert/update/delete runs in its own JDBC transaction (commit or rollback), so a crash never leaves a half-written checkpoint.
  • Because state is in the database, a paused incident survives an application restart and can be resumed by approving it afterwards.
  • Graph is compiled with releaseThread(false) so the final state stays readable after the run ends.

9. Service and REST API

IncidentService saves the alert, seeds the simulation, runs the graph (draining the stream until END or the interrupt), applies the human decision with updateState, resumes with GraphInput.resume(), and syncs the final status back to the Alerts row.

MethodPathDescription
POST/incidentsBody {"serviceName","message"}. Runs until finished or paused for approval.
POST/incidents/{id}/approvalBody {"approved":true|false}. 409 if the incident is not waiting.
GET/incidents/{id}Current status, findings, plan, timeline, awaitingApproval.
GET/incidents/{id}/auditAudit trail from the database.

Typical scenario

1. POST /incidents                -> attempt 1: SCALE_OUT (LOW) runs automatically, still unhealthy
                                    attempt 2: KILL_IDLE_SESSIONS (HIGH) -> paused, awaitingApproval=true
2. POST /incidents/{id}/approval  -> executes; leak refills the pool -> attempt 3: RESTART_SERVICE (HIGH) -> paused again
3. POST /incidents/{id}/approval  -> restart clears the leak -> verify OK -> status RESOLVED

10. Configuration and Docker

  • docker-compose.yml: service mssql (SQL Server 2022, healthcheck, persistent volume mssql_data, host port 1434 by default via MSSQL_PORT) and one-shot mssql-init that creates sag once healthy.
  • application.yml: JDBC URL with encrypt=true;trustServerCertificate=true, Hikari pool size, ddl-auto: update, incident.max-attempts, and LLM settings (base-url, api-key, model).
  • Environment overrides: MSSQL_HOST, MSSQL_PORT, MSSQL_SA_PASSWORD, OPENAI_API_KEY. The default SA password is for local development only.

11. Tests (IncidentFlowTest)

  • Full loop with approvals: pause, checkpoint row exists, approve twice, ends RESOLVED, audit shows all three executed actions.
  • Rejection: dangerous command never executes and a further approval returns an error.
  • Parallel branches: all three lookup nodes wrote audit rows.

They are integration tests and need the SQL Server container running.

12. How to run

docker compose up -d
mvn test
mvn spring-boot:run        # http://localhost:8080

Limitations

  • Infrastructure actions are simulated; replace SimulatedEnvironment with real executors for production.
  • LangGraph4j has no Send API, so parallelism uses multiple outgoing edges.
  • The OpenAI path is untested without an API key; no deadlock stress test yet.
