Order MCP Server

A simple Model Context Protocol (MCP) server built with Java 17, Spring Boot 3.3 and Spring AI. It exposes two existing order APIs (search and create) as MCP tools so an AI assistant can call them from natural language.

1. Architecture

OrderServicein-memory store

2. How the MCP "knows" which API to call

The server does not parse the user's sentence. Each API is published as a tool with a name, a description and a parameter schema. The LLM in the client reads these descriptions and decides which tool to call and with which arguments.

Prompt: "find the order 123, and create an order"
1. LLM matches "find ... order 123" → calls searchOrder(orderId=123)
2. LLM matches "create an order" → asks for / fills customer, product, quantity → calls createOrder(...)
3. LLM summarizes both results for the user

8. Step-by-step: how this project was built (and why)

#StepWhat we didWhy
1Create the Maven projectpom.xml with Spring Boot 3.3 parent, Spring AI BOM and spring-ai-starter-mcp-server-webmvc. The starter auto-configures the MCP protocol, SSE transport and tool registration, so we write no protocol code. The BOM keeps Spring AI versions consistent. Java 17 is Spring Boot 3's minimum.
2Add the application classOrderMcpApplication with a ToolCallbackProvider bean built from OrderTools. MCP only exposes tools that are registered. The bean is what turns @Tool methods into MCP tools.
3Define the modelsOrder and CreateOrderRequest as Java records. Records are short, immutable and serialize to JSON directly. They give the API and tools a shared, typed contract.
4Add the serviceOrderService with an in-memory map, seeded with order 123. Stands in for a real database so the example stays simple, and gives us data to search right away.
5Add the REST controllerGET /api/orders/{id} and POST /api/orders. These are the "existing APIs" the MCP must cover. Keeping them as normal REST means other clients can use them too, and the MCP is just a thin layer on top.
6Write the MCP toolsOrderTools: searchOrder and createOrder annotated with @Tool and @ToolParam, calling the REST APIs via RestClient. This is the heart of the project. The tool description is what the LLM reads to decide which API fits the request, so descriptions are written around user phrasing ("find order", "create an order"). Calling REST rather than the service keeps the MCP valid for a separate order service later.
7Return typed resultssearchOrder returns OrderSearchResult(found, order, message), not Object. Spring AI silently ignores tool methods with a generic/functional return type. A typed result also lets the LLM tell "not found" apart from an error.
8Minimal configurationapplication.yml: port 8080, MCP name and version. Defaults cover everything else (SSE at /sse). The name and version only make the server identifiable in clients.
9Build and testmvn package, then call the tools over the SSE endpoint (tools/call). Proves the tools are registered and return correct data, independent of any AI client. This is how we caught the ignored-tool problem in step 7.
10ContainerizeDockerfile (multi-stage) and docker-compose.yml mapping 9004:8080. Makes it runnable anywhere without installing Java or Maven. The multi-stage build keeps the final image small. Host port 9004 avoids clashes with other local services on 8080.
11Connect a clientAdd the SSE URL to the client's MCP config and try the sample prompt. The client's LLM discovers the tools via tools/list and chooses which to call, so no routing logic is needed on the server.

9. How to test

Use 8080 when running with java -jar, or 9004 when running with Docker. Examples below use 9004. In Postman: Import → Raw text and paste any curl command below.

Testing is done in three layers. Each layer proves one thing, and a failure tells you where the problem is:

LayerWhat it provesIf it fails
9.1 REST APIsThe business logic and the two "existing APIs" work on their own, with no MCP involvedBug in OrderController / OrderService
9.2 MCP protocolThe MCP server exposes the tools, with the right names, descriptions and parameters, and each tool really calls the REST APIBug in OrderTools, tool registration, or the SSE/MCP config
9.3 Agent (Copilot CLI)A model reads a plain sentence and picks the right tool(s) and argumentsPoor tool descriptions, or a provider / model configuration problem

Run the layers in order. The sample data is an in-memory store seeded with order 123 (Alice, Laptop, 1). New orders get IDs 124, 125, ... and are lost when the server restarts.

9.1 Test the REST APIs

Goal: confirm the two existing APIs behave correctly before MCP wraps them. The MCP tools only call these endpoints, so if these are wrong, everything above is wrong.

TestWhat is being testedcURLExpected

curl http://localhost:9004/api/orders/123

Invoke-RestMethod -Method Post http://localhost:9004/api/orders `
  -ContentType application/json `
  -Body '{"customerName":"Bob","product":"Phone","quantity":2}'

9.2 Test the MCP tools (SSE transport)

Goal: act as an MCP client by hand, to prove that the server speaks MCP and the tools work. This is exactly what Copilot CLI does for you automatically.

MCP over SSE uses two connections: keep the SSE stream open to receive responses, and POST requests to the session endpoint. The POST only returns Accepted; the real JSON-RPC result is printed in the terminal that holds the stream. In Postman, create a GET request to /sse (keeps streaming) and send the POSTs from a second request.

  1. Open the stream (terminal 1, leave it running). Tests: the SSE endpoint is up and creates a session. It prints an endpoint such as /mcp/message?sessionId=abc-123; use that sessionId below: 
    curl -N http://localhost:9004/sse
  2. Initialize (terminal 2; replace the sessionId). Tests: the MCP handshake. The result in terminal 1 contains the server name order-mcp-server and its capabilities. MCP requires this before any other call: 
    curl -X POST "http://localhost:9004/mcp/message?sessionId=abc-123" \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"curl","version":"1"}}}'

curl -X POST "http://localhost:9004/mcp/message?sessionId=abc-123" \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","method":"notifications/initialized"}'
  3. List tools. Tests: tool discovery, which is how a client's LLM learns what it can call. Expect searchOrder and createOrder, each with its description and input schema. If a tool is missing here, no model can ever use it: 
    curl -X POST "http://localhost:9004/mcp/message?sessionId=abc-123" \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/list"}'
  4. Call searchOrder. Tests: the read tool end to end (MCP → OrderTools → REST → service). Expect {"found":true,"order":{...},"message":"Order found"}. Change orderId to 999 to check found:false: 
    curl -X POST "http://localhost:9004/mcp/message?sessionId=abc-123" \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"searchOrder","arguments":{"orderId":123}}}'
  5. Call createOrder. Tests: the write tool end to end, including argument mapping (customerName, product, quantity). Expect the new order with status CREATED: 
    curl -X POST "http://localhost:9004/mcp/message?sessionId=abc-123" \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":4,"method":"tools/call","params":{"name":"createOrder","arguments":{"customerName":"Bob","product":"Phone","quantity":2}}}'
  6. Confirm the write really happened (REST, not MCP). Tests: the tool changed the same data the REST API reads: 
    curl http://localhost:9004/api/orders/124

Common errors: 400 on /mcp/message usually means broken JSON quoting (on Windows use curl.exe with a body file: -d "@body.json"); an unknown or expired sessionId means reopen the stream and use the new id.

9.3 Test with Copilot CLI as the agent (bring your own model)

The server has no LLM of its own. Copilot CLI acts as the agent: it uses your model provider (BYOK) and calls the MCP tools. Start the server (docker compose up -d --build), then:

# PowerShell: provider settings (Azure example)
$env:COPILOT_PROVIDER_TYPE="azure"
$env:COPILOT_PROVIDER_BASE_URL="https://<resource>.openai.azure.com"
$env:COPILOT_PROVIDER_API_KEY="<your key>"
$env:COPILOT_PROVIDER_MODEL_ID="gpt-5.3-codex"
$env:COPILOT_PROVIDER_WIRE_MODEL="<deployment name>"
$env:COPILOT_PROVIDER_WIRE_API="responses"
# OpenAI instead: TYPE=openai, BASE_URL=https://api.openai.com/v1, API_KEY=sk-...

# register the MCP server once
copilot mcp add --transport sse order-mcp http://localhost:9004/sse

9.4 Test with an external AI client

Add the SSE URL to your client, then ask: "Find the order 123, and create an order for Bob, 2 Phones." Check that the client calls searchOrder first, then createOrder. Alternatively use the MCP Inspector: npx @modelcontextprotocol/inspector → transport SSE → URL http://localhost:9004/sse.

10. Notes

  • Data is in memory and resets on restart; the API is a stand-in for a real order service.
  • To target a separate order service, set order.api.base-url (default: this app).
